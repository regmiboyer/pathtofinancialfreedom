Workflow — click any step to see details
1
📋 Product Manager
Create User Story
PM receives the raw feature request and converts it into a structured user story with acceptance criteria, story points, and out-of-scope boundaries.
→ Output: user_story.json {story_id, acceptance_criteria[], story_points}
2
💻 Developer
Create Jira Ticket
Developer reads the user story and creates a Jira ticket with implementation plan, affected components, and test case hints before writing a single line of code.
→ Output: jira_ticket.json {ticket_id, implementation_plan[], files_to_change[]}
3
💻 Developer
Implement Feature
Developer produces exact search/replace code patches for index.html. Each change includes a description, the old code string to find, and the new code string to insert.
→ Output: code_changes.json {changes[{search, replace, description}], testing_notes}
4
🧪 QA Engineer
QA Review (Iteration 1…3)
QA checks every acceptance criterion, hunts for edge-case bugs (zero inputs, max values, JS errors), and returns a structured review with bug severity and reproduction steps.
→ Output: qa_review.json {status: approved|rejected, bugs[], passed_criteria[]}
↩
If rejected: bugs sent back to Developer → fix → re-QA (max 3 iterations)
4b
💻 Developer
Bug Fix (if QA rejected)
Developer receives the bug report, targets each BUG-N item, and produces new search/replace patches. Loops back to QA until all criteria pass or max iterations reached.
→ Output: code_changes.json {iteration: N, changes[{description, search, replace}]}
5
🚢 Release Manager
Apply Patches → Screenshot → Release
Release Agent applies all search/replace patches to index.html, backs up the old file, opens the browser, triggers a macOS screencapture for visual proof, then writes a release manifest and changelog entry.
→ Output: releases/release-1.0.XXX.json · screenshots/release-v1.0.XXX.png

📋 Product Manager

You are the Product Manager for the Investment Planner — a single-file HTML app with 8 investment strategies.

Responsibilities:
• Convert raw feature requests into precise user stories.
• Write every acceptance criterion as a testable pass/fail statement.
